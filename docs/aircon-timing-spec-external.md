# 冷房タイミングガイド（外部公開版） — 要件定義・基本設計書

最終更新: 2026-06-19

> 本書は**外部公開版**の定義書です。実測値連携・予冷シミュレーションなどを含む内部用フル機能版は別ドキュメントとして管理します。

---

## 1. 要件定義

### 1.1 背景・目的

エアコンの冷房は外気温が低いほど効率（COP）が高い。この特性を利用し、「外気温が低い時間帯に一気に冷やし、ピーク時は維持運転にする」予冷戦略を、データに基づいて判断できるようにする。

既存サービス（メーカー純正アプリ等）はハード依存・機種限定であるため、外部APIから必要な情報のみを取得し、誰でも使える形で表示するWebサービスを作る。

### 1.2 スコープ

**やること**
- 当日（24時間）の外気温・湿度予報の取得と可視化
- 外気温ベースの冷房効率スコア表示
- 「今が好機か」を示す自動コメント（ルールベース、無料）
- Web上での公開（PC/モバイル両対応）

**やらないこと（初期スコープ外）**
- 実際のエアコン操作（IoT連携）
- ユーザー認証・アカウント管理
- 複数日先の予報
- 電力需給ひっ迫情報との連携（将来拡張として記載のみ）
- **AI（LLM API）連携** — 課金が発生するため採用しない。判断ロジックは全てルールベースで実現する（1.7参照）

### 1.3 利用者と利用シーン

| 項目 | 内容 |
|---|---|
| 利用者 | サービス開発者本人および同様のニーズを持つ個人 |
| 利用シーン | 朝の出発前、帰宅前、休日の日中に「今からエアコンをどう使うか」を判断する場面 |
| デバイス | スマートフォン・PC/タブレット両方（レスポンシブ対応） |

### 1.4 機能要件

| ID | 機能 | 概要 | 優先度 |
|----|------|------|--------|
| F-01 | 位置情報取得 | ブラウザGeolocationで現在地を取得。拒否時は東京固定 | 必須 |
| F-02 | 気温・湿度予報取得 | Open-Meteo APIから当日24時間分を取得 | 必須 |
| F-03 | 効率スコア計算 | 気温を4段階（最高/良好/普通/非効率）に分類 | 必須 |
| F-04 | グラフ表示 | 24時間の気温推移を折れ線グラフ表示、効率帯を背景色で表現 | 必須 |
| F-05 | 自動コメント生成 | ルールベースで「いつが好機か」を文章化 | 必須 |
| F-06 | 統計サマリー | 最低/最高気温、高効率時間数を表示 | 必須 |
| F-07 | 時間別バー表示 | スマホでも見やすい簡易ビジュアル | 必須 |
| F-08 | エラー表示 | API失敗時にユーザーへ通知 | 必須 |

### 1.5 コスト方針

本サービスは**完全無料運用**を前提とする。

- 気象データ取得：Open-Meteo（無料・APIキー不要・商用利用も無料枠内可）
- ホスティング：Vercel無料プラン（個人利用なら帯域・実行時間とも収まる想定）
- サーバーサイド処理：不要（クライアントから直接Open-Meteoを呼ぶ構成のため、Vercel Functionsも不要）
- LLM API等の従量課金サービスは採用しない

### 1.6 非機能要件

| 項目 | 要件 |
|---|---|
| 可用性 | 個人利用前提。SLA要件なし |
| パフォーマンス | 初回表示3秒以内（気象API応答に依存） |
| セキュリティ | 外部に秘匿すべきAPIキーを持たない構成（Open-Meteoは認証不要） |
| コスト | 完全無料（1.5参照） |
| 対応ブラウザ | モダンブラウザ（Chrome/Safari/Edge最新版） |
| 多言語対応 | 日本語のみ（初期） |

### 1.7 制約・前提

- Geolocationが使えない/拒否される場合があるため、フォールバック地点（東京）を用意する
- Open-Meteoは認証不要だが、SLA保証はないため障害時の表示崩れを想定する
- 「効率の良いタイミング」の判断は気温閾値によるルールベースとし、AI（LLM）には依存しない

## 2. 基本設計

### 2.1 システム構成図

```
┌─────────────┐      ①位置情報取得       ┌──────────────────┐
│   ブラウザ    │ ──────────────────────> │  Geolocation API   │
│ (React SPA)  │ <────────────────────── │  (ブラウザ標準)      │
└──────┬──────┘                          └──────────────────┘
       │
       │ ②気温・湿度予報取得 (GET、認証不要)
       ▼
┌─────────────────┐
│  Open-Meteo API   │  ※無料・APIキー不要
└─────────────────┘
       │
       │ ③表示用データに加工（フロント側で計算）
       ▼
┌─────────────┐
│   ブラウザ    │  グラフ・統計・自動コメントを表示
│ (画面表示)    │
└─────────────┘
```

サーバーサイド処理が不要なため、構成は「静的ホスティング＋クライアントから外部APIを直接呼ぶ」のみで完結する。

### 2.2 ホスティング構成

| レイヤー | 技術 | 役割 |
|---|---|---|
| フロントエンド | React + Vite | SPA。グラフ描画・状態管理・効率判定 |
| ホスティング | Vercel（または同等の静的ホスティング） | 静的ファイル配信のみ |
| 外部API | Open-Meteo | 気象データ取得（唯一の外部依存） |

### 2.3 データフロー

1. ブラウザがGeolocation APIで緯度経度を取得（拒否時は東京固定値）
2. 取得した緯度経度でOpen-Meteoに直接リクエスト（CORS許可済み、サーバー経由不要）
3. レスポンスの`temperature_2m`・`relative_humidity_2m`配列を時間ごとの配列に整形
4. 各時間の気温から効率スコア（excellent/good/fair/poor）を算出
5. グラフ・統計・自動コメントを画面に反映（すべてフロント側のロジックで完結）

### 2.4 効率スコア判定ロジック

| 外気温 | スコア | 表示色 |
|---|---|---|
| 〜24℃ | excellent（最高） | 緑 #34d399 |
| 25〜27℃ | good（良好） | 黄 #fbbf24 |
| 28〜31℃ | fair（普通） | 橙 #fb923c |
| 32℃〜 | poor（非効率） | 赤 #f87171 |

> 補足: 現状は気温のみで判定。室外機の効率は湿度や日射の影響も受けるため、将来的に体感温度（暑さ指数相当）への置き換えを検討（3.2参照）。

### 2.5 自動コメント生成ロジック（疑似コード）

```
good = 気温が excellent または good の時間帯を抽出
連続区間（windows）にグルーピング
最長の区間を topWindow とする

if topWindow が存在しない:
    「本日は一日中気温が高め。早い時間帯での予冷を推奨」

else if 現在時刻が topWindow の範囲内:
    「✅ 今が好機。一気に冷やすタイミング」

else if topWindow がこれから来る:
    「⏰ ◯時〜◯時が好機。先行冷房推奨」

else（既に過ぎている）:
    「🕐 好機は過ぎた。夜以降に再チャンスの可能性」
```

### 2.7 外部API仕様

**Open-Meteo Forecast API**
```
GET https://api.open-meteo.com/v1/forecast
  ?latitude={lat}
  &longitude={lon}
  &hourly=temperature_2m,relative_humidity_2m
  &forecast_days=1
  &timezone=Asia%2FTokyo
```
- 認証不要、レート制限緩い（個人利用で問題なし）
- レスポンスは`hourly.time[]`（ISO8601文字列の配列）と対応する`temperature_2m[]`、`relative_humidity_2m[]`

本サービスが利用する外部APIはこれ1つのみ。

### 2.8 エラーハンドリング方針

| 状況 | 挙動 |
|---|---|
| Geolocation拒否/失敗 | 東京固定値にフォールバック、ラベルで明示 |
| Open-Meteo通信失敗 | エラーメッセージ表示、再読み込みを促す |
| データ0件 | グラフ非表示、ローディングまたはエラー文言を表示 |

### 2.9 セキュリティ設計

- 秘匿すべきAPIキーを持たない構成のため、キー漏洩リスクそのものが存在しない
- 外部送信される情報は緯度経度のみ（Open-Meteoへのリクエスト時）。個人情報の保存・送信は行わない

## 3. 拡張候補（将来検討）

### 3.1 電力需給・料金との連携
- 各電力会社の「でんき予報」やOCCTOの広域予備率情報と連携し、「電気代が安い＋効率が良い」時間帯を複合判定する

### 3.2 体感温度ベースの判定への高度化
- 気温のみでなく、湿度を加味した暑さ指数（WBGT近似）で効率スコアを算出する

### 3.3 通知機能
- 「好機が始まった」タイミングでブラウザ通知 or LINE通知を送る

### 3.4 過去データとの比較
- 当日と平年値・前日の比較を表示し、傾向を把握しやすくする

### 3.5（参考・非推奨）AIによる自然文アドバイス
- LLM APIで「もっと自然な言い回しのアドバイス」を生成することは技術的には可能だが、従量課金が発生するため本サービスでは採用しない。ルールベースの自動コメント（F-05）で要件は満たせる判断。
