# 冷房タイミングガイド（内部版） — 要件定義・基本設計書

最終更新: 2026-06-19

> 本書は**内部専用版**の定義書です。外部公開する無料スリム版は別ドキュメント（`aircon-timing-spec-external.md`）を参照してください。本版はHome Assistant経由の実測値連携と予冷シミュレーションを含むフル機能版です。

---

## 1. 要件定義

### 1.1 背景・目的

外部公開版（外気温予報のみ）に対し、内部版では**自宅の実測値**（室温・湿度）と**エアコン・部屋の特性**を組み合わせ、「いつから何分冷房を強めにかければ、いつ目標室温に到達し、その後どう維持運転すればよいか」を具体的に計算する。

home labの既存基盤（Home Assistant、Cloudflare Tunnel経由の外部アクセス）に統合し、自分専用ツールとして運用する。

### 1.2 スコープ

**やること**
- Home Assistant経由での室温・湿度の実測値取得（センサー実体はNature Remo。HA上でNature Remo連携済みの前提）
- 外気温予報（Open-Meteo、外部公開版と共通）との組み合わせ
- 部屋・エアコンのプロファイル設定（畳数、断熱性、エアコン性能等）
- 予冷シミュレーション：目標室温までの到達時間の計算
- 「いつ強運転を開始すべきか」の逆算提示
- 強運転→維持運転への切り替えタイミング提示
- kumaguma0918.com サブドメインでの内部限定公開（Cloudflare Access等で保護）

**やらないこと（初期スコープ外）**
- エアコンの自動制御（HA経由でのON/OFF・温度設定の自動操作）→ 将来拡張（3.3）
- 複数部屋・複数台エアコンの同時最適化
- 学習機能（過去の実績から自動補正するMLモデル）→ 将来拡張（3.4）
- AI（LLM API）連携 → 外部版と同じ方針で不採用。計算はすべて物理モデル・ルールベースで実施

### 1.3 利用者と利用シーン

| 項目 | 内容 |
|---|---|
| 利用者 | ショウタ本人のみ |
| 利用シーン | 外出先から帰宅前に確認、または在宅時に「あと何分で涼しくなるか」を確認する場面 |
| デバイス | スマートフォン（外出先からCloudflare Tunnel経由でアクセス） |
| アクセス制御 | Cloudflare Access（既存のEntra ID + FIDO2構成を流用） |

### 1.4 機能要件

| ID | 機能 | 概要 | 優先度 |
|----|------|------|--------|
| F-01 | 外気温予報取得 | Open-Meteoから当日24時間分を取得（外部版と共通ロジック） | 必須 |
| F-02 | 室内実測値取得 | Home Assistant API経由で現在の室温・湿度を取得（センサー実体: Nature Remo）。取得時刻（タイムスタンプ）も併せて表示する | 必須 |
| F-03 | 部屋・機器プロファイル管理 | 畳数、断熱性、エアコンの冷房能力（kW）等を設定・保存 | 必須 |
| F-04 | 予冷シミュレーション計算 | 現在室温→目標室温までの到達時間を物理モデルで計算。静的近似モデルである旨をUI上に注記する（2.4.2参照） | 必須 |
| F-05 | 逆算タイミング提示 | 「外出先から何時に帰るなら何時に運転開始すべきか」を算出。到着予定時刻を変更した場合は再計算ボタンで`/api/simulate`を再呼び出しする | 必須 |
| F-06 | 強運転/維持運転の切替提案 | 目標到達後、外気温の推移を見て維持運転への切替時刻を提示 | 必須 |
| F-07 | 効率スコア表示 | 外部版と同じ気温ベースの効率可視化 | 必須 |
| F-08 | 実測値とシミュレーションの比較表示 | 計算予測 vs 実際の室温推移をグラフで比較（精度検証用） | 必須 |
| F-09 | アクセス制御 | Cloudflare Access配下に配置し本人のみアクセス可能にする | 必須 |
| F-10 | エラー表示 | HA未接続・API失敗時の通知。取得値が30分以上古い場合も「データが古い」と表示する（2.8参照） | 必須 |

### 1.5 コスト方針

- Open-Meteo：無料
- Home Assistant：自宅サーバーで稼働中の既存資産を利用（追加コストなし）
- ホスティング：自宅home lab内（既存のCloudflare Tunnel経由で公開、Vercel等の外部ホスティングは使わない想定）
- LLM API等の従量課金サービスは外部版同様不採用

### 1.6 非機能要件

| 項目 | 要件 |
|---|---|
| 可用性 | 個人利用前提。home labのネットワーク状態に依存（既知の制約として許容） |
| パフォーマンス | シミュレーション計算は同期的に1秒以内で完了する想定（軽量な物理モデルのため） |
| セキュリティ | Cloudflare Access配下に配置し、Entra ID認証必須。HAのAPIトークンは環境変数で管理しコードに含めない |
| データ保存 | 部屋プロファイルはローカル（SQLite等）に保存。実測値の長期保存はHA側のHistory機能に委譲し本ツールでは持たない |
| 対応ブラウザ | モダンブラウザ（モバイル中心） |

### 1.7 制約・前提

- Home AssistantのAPIから取得できる室温センサーが既に存在していることを前提とする（確定: Nature Remoを室温・湿度センサーとして使用。HA上でNature Remo連携が設定済みであることを前提とする）
- 確定: Nature Remoはクラウド経由でのデータ更新のため、**取得値が数分〜十数分前の値になる可能性がある**。シミュレーションは「現在室温」として扱うが、UI上に実測値の取得時刻（タイムスタンプ）を併記し、利用者がズレを認識できるようにする
- 確認推奨: Nature Remo本体の設置位置（コンセント付近等）によっては、部屋の代表的な温度と実測値がズレる場合がある。設置位置が窓際・日射の影響を受けやすい場所でないか、運用開始前に一度確認する
- 予冷シミュレーションは簡易物理モデルであり、完全な熱力学計算ではない。実測値との比較（F-08）で継続的に精度を確認し、必要に応じてパラメータを調整する運用とする
- 帰宅時間の入力はユーザーが手動で行う（カレンダー連携等の自動化は将来拡張）
- 確定: 湿度（F-02で取得）は**表示用途のみとし、予冷シミュレーションの計算には使用しない**。将来、暑さ指数（WBGT近似）等への計算高度化を行う場合に再利用する想定（3.2参照）
- 確定: 本サービスは**冷房（夏季）利用のみを対象**とする。暖房（冬季）への対応は初期スコープ外（暖房は熱負荷の方向が逆になり別モデルが必要なため）

## 2. 基本設計

### 2.1 システム構成図

```
┌──────────────┐
│ スマートフォン  │
│ (ブラウザ)      │
└──────┬───────┘
       │ ① HTTPS (Cloudflare Access経由、Entra ID認証)
       ▼
┌─────────────────────────┐
│ Cloudflare Tunnel          │  既存のkumaguma-tunnel基盤
└──────────┬──────────────┘
           │
           ▼
┌─────────────────────────────────┐
│ アプリ本体（home lab内, 例: Docker host） │
│  - フロントエンド (React)              │
│  - バックエンド (FastAPI等)            │
│      ├─ ②外気温取得 → Open-Meteo      │
│      ├─ ③室内実測値取得 → Home Assistant │
│      ├─ ④部屋プロファイルDB (SQLite)    │
│      └─ ⑤予冷シミュレーション計算ロジック │
└─────────────────────────────────┘
```

外部版と異なり、バックエンド（API集約・計算処理）を持つ構成とする。理由：
- Home AssistantのAPIトークンをフロントに露出させたくない
- 予冷シミュレーションの計算ロジックをサーバー側に集約し、将来の自動制御連携（3.3）に拡張しやすくする

### 2.2 ホスティング構成

| レイヤー | 技術 | 役割 |
|---|---|---|
| フロントエンド | React + Vite | UI表示 |
| バックエンド | FastAPI（Python） | API集約、シミュレーション計算 |
| 実行環境 | home lab内Dockerホスト（既存資産、192.168.100.30） | コンテナとして稼働。ESPRIMO Q556/Rは対象外（既存Dockerホストに確定） |
| 公開経路 | Cloudflare Tunnel + Access | 外部からの安全なアクセス |
| データ保存 | SQLite（部屋プロファイル） | 軽量・追加ミドルウェア不要 |
| 外部API | Open-Meteo、Home Assistant REST API | データ取得元 |

### 2.3 データフロー

1. ユーザーがブラウザでアクセス → Cloudflare AccessでEntra ID認証
2. フロントエンドがバックエンドAPIを呼び出し、以下を要求：
   - 当日の外気温予報（バックエンドがOpen-Meteoから取得）
   - 現在の室温・湿度（バックエンドがHome Assistant REST APIから取得）
   - 保存済みの部屋プロファイル（畳数、断熱性、エアコン性能）
3. ユーザーが目標室温・到着予定時刻を入力
4. バックエンドが予冷シミュレーションを計算し、以下を返却：
   - 推奨運転開始時刻
   - 目標室温到達までの推定時間
   - 強運転→維持運転の切替推奨タイミング
5. フロントエンドがグラフ・タイムラインで結果を表示
6. （F-08）実際の室温推移をHAから定期取得し、予測値と並べて比較表示

### 2.4 予冷シミュレーションの計算モデル

#### 2.4.1 入力パラメータ

| パラメータ | 取得元 | 例 |
|---|---|---|
| 現在室温 | Home Assistant（実測） | 29.5℃ |
| 目標室温 | ユーザー入力 | 26.0℃ |
| 外気温（時間別） | Open-Meteo | 各時間の予報値 |
| 部屋の畳数 | プロファイル設定 | 14畳 |
| 断熱性レベル | プロファイル設定（簡易区分） | 木造/RC造などの区分で係数を補正 |
| エアコン冷房能力 | プロファイル設定 | 4.0kW等、機種スペックから入力 |
| 室内発熱（人数・PC等） | プロファイル設定（簡易） | 軽い補正項として扱う |

#### 2.4.2 モデルの考え方

簡易熱負荷モデルを採用する（厳密な熱力学シミュレーションは行わない）。

**確定: 単位をSI単位（kW・kJ・℃・秒）で明示的に統一し、畳数の重複カウントを避ける形に整理した。**

```
① 熱侵入(kW) = 断熱性係数(kW/畳/℃) × 畳数 × (外気温 - 目標室温)

② 実効冷房能力(kW) = エアコン冷房能力 - 熱侵入 - 室内発熱(kW固定値)

③ 室内の熱容量(kJ/℃) = 熱容量係数(kJ/℃/畳) × 畳数

④ 除去すべき熱量(kJ) = 熱容量 × (現在室温 - 目標室温)

⑤ 到達時間(分) = 除去すべき熱量(kJ) ÷ 実効冷房能力(kW) ÷ 60
   ※ kW = kJ/秒 のため、kJ ÷ kW = 秒
```

**初期係数（仮値、運用しながら補正）：**

| 係数 | 値（仮） | 単位 |
|---|---|---|
| 断熱性係数 | 0.012 | kW/畳/℃ |
| 室内発熱 | 0.3 | kW（固定） |
| 熱容量係数 | 60 | kJ/℃/畳 |

**検証例（14畳・外気温33℃・目標26℃・現在29.5℃・エアコン4.0kW）：**

```
熱侵入 = 0.012 × 14 × (33-26) = 1.18 kW
実効冷房能力 = 4.0 - 1.18 - 0.3 = 2.52 kW
熱容量 = 60 × 14 = 840 kJ/℃
除去すべき熱量 = 840 × (29.5-26) = 2,940 kJ
到達時間 = 2,940 ÷ 2.52 ÷ 60 ≈ 19.4分
```

実効冷房能力が0以下になる場合（外気温が高すぎる・エアコン能力不足等）は「目標室温への到達は困難」として警告表示する（2.8参照）。

> 確定: このモデルは「外気温・冷房能力が計算時点から一定」という前提の静的近似モデルである。実際は強運転中も外気温が変動するため、到達時間はあくまで目安。UI上に「簡易計算のため目安です」等のツールチップ・注記を表示する（F-04の表示要件として追加）。

> 確定: 室内発熱の初期値0.3kWは「居住者1名＋PC等の電子機器」を想定した仮の固定値。`occupant_load`としてプロファイルに保持するが、初期実装では固定値運用とし、人数や機器構成による動的変動は将来拡張（3.4以降）で検討する。コード上はこの根拠をコメントで残す。

#### 2.4.3 出力

- 推奨運転開始時刻（逆算）
- 強運転継続時間（分）
- 維持運転への切替推奨時刻
- 維持運転時の推奨設定温度（外気温推移に応じて）

### 2.5 部屋・機器プロファイル設計

**確定: ワンルーム1部屋構成のため、プロファイルは単一固定とする。**複数部屋管理のUI・テーブル設計は不要。設定値は以下の固定パラメータとしてシンプルなJSON/設定ファイルまたは単一行のSQLiteテーブルで保持する。

| 項目 | 型 | 備考 |
|---|---|---|
| room_name | string | 例: "Yashioワンルーム" |
| tatami_size | number | 畳数 |
| insulation_level | enum | 木造/RC造/その他、簡易区分 |
| aircon_cooling_kw | number | エアコンスペック表記値 |
| occupant_load | number | 簡易固定値（人数等で補正） |
| updated_at | datetime | 係数調整時に更新 |

> 複数部屋・複数プロファイルの管理機能（プロファイル一覧UI、profile_id切り替え等）は3.4「複数部屋対応」に格下げし、初期スコープからは除外する。

### 2.7 外部・内部API仕様

**Open-Meteo（外部版と共通）**
```
GET https://api.open-meteo.com/v1/forecast?...
```

**Home Assistant REST API（想定）**
```
GET {HA_BASE_URL}/api/states/{entity_id}
Header: Authorization: Bearer {HA_LONG_LIVED_TOKEN}
```
- `entity_id`はプロファイルごとに室温・湿度センサーを紐付け設定
- `HA_LONG_LIVED_TOKEN`はバックエンドの環境変数として保持（フロントに露出させない）

**バックエンド内部API（フロントエンド向け）**
```
GET  /api/status          → 現在の室温・外気温まとめ取得
GET  /api/profile          → プロファイル取得（単一固定）
POST /api/profile          → プロファイル更新
POST /api/simulate          → シミュレーション実行
  Body: { target_temp, arrival_time }
  Response: { start_time, strong_duration_min, switch_time, predicted_curve[] }
```

### 2.8 エラーハンドリング方針

| 状況 | 挙動 |
|---|---|
| Home Assistant接続失敗 | 室温は「取得不可」と表示し、外気温のみのシンプル表示にフォールバック |
| Open-Meteo通信失敗 | 外部版と同様、エラー表示 |
| プロファイル未登録 | シミュレーション実行不可。先にプロファイル登録を促す |
| シミュレーション計算異常値（負の時間、実効冷房能力0以下、極端な長時間等） | 「計算できませんでした」または「目標室温への到達は困難です」と表示。**確定: 到達時間が480分（8時間）を超える場合も異常値として警告表示し、入力値（目標室温・到着予定時刻）の見直しを促す** |
| Home Assistant応答が極端に古い | **確定: 取得値のタイムスタンプが30分以上前の場合「データが古い」旨をUIに表示する**（Nature Remoの通常更新間隔15〜20分に対し、誤検知と検知漏れのバランスを取った値） |

> タイムゾーンはOpen-Meteo・Home Assistant双方とも`Asia/Tokyo`固定で運用し、ズレが生じないようにする。

### 2.9 セキュリティ設計

- 外部公開せず、Cloudflare Access（Entra ID + FIDO2）配下に配置
- Home AssistantのLong-Lived Access Tokenはバックエンドの環境変数で管理し、フロントエンドに渡さない
- バックエンドAPIは内部ネットワーク・Cloudflare Tunnel経由のみで到達可能とし、直接のポート開放は行わない
- 確定: `.env`ファイルは`.gitignore`に登録し、リポジトリに含めない。可能であればDocker Composeの`secrets`機能を使い、環境変数より一段階強いシークレット管理を行う
- 確定: 本コンテナは他のhome lab上の既存コンテナとDockerネットワークを分離する（専用のdocker networkを割り当て、不要な疎通を持たせない）

## 3. 拡張候補（将来検討）

### 3.1 自動制御連携
- シミュレーション結果に基づき、Home Assistant経由でエアコンを自動起動・温度設定する

### 3.2 帰宅時間の自動取得
- カレンダー連携や位置情報（Googleタイムライン等）から到着予定時刻を自動推定する

### 3.3 学習による係数補正
- F-08の予測vs実測の差分を蓄積し、断熱性係数・熱容量係数を自動補正する仕組み（簡易回帰等）

### 3.4 複数部屋対応
- 複数の部屋・エアコンを同時に管理し、優先順位をつけて運転計画を立てる

### 3.5 外部公開版へのフィードバック
- 内部版で検証した効率スコアの閾値や物理モデルの知見を、外部公開版の精度向上に反映する

### 3.6 実行トラッキング
- シミュレーションで提示した「運転開始時刻」に対し、ユーザーが実際にエアコンを動かしたかを記録する手段がない（自動制御3.1とセットで検討すると効率的）

### 3.7 履行ログ・利用履歴
- 1日に複数回シミュレーションを行った場合の履行ログ（いつ計算し、いつ実際に冷房したか）を残す機能。F-08の精度検証データとしても活用可能
