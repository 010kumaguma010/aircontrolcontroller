## 1. 要件定義

### 1.1 背景・目的

外部公開版の背景（外部版1.1参照）と同じく、「エアコンの冷房は外気温が低いほど効率（COP）が高い」という特性を利用し、**外気温が低く効率の良い時間帯に一気に冷やし、効率が悪化するタイミングで維持運転に切り替える**予冷戦略を軸とする。

内部版では、これを外部版の予報のみの可視化にとどめず、**自宅の実測値**（室温・湿度）と**エアコン・部屋の特性**を組み合わせて、「本日の効率窓（外気温が低く効率の良い連続時間帯）を使って、いつ強運転を始め、いつ目標室温に到達し、いつ維持運転に切り替えるべきか」を具体的に計算する。

home labの既存基盤（Home Assistant、Cloudflare Tunnel経由の外部アクセス）に統合し、自分専用ツールとして運用する。

### 1.2 スコープ

**やること**
- Home Assistant経由での室温・湿度の実測値取得（センサー実体はNature Remo。HA上でNature Remo連携済みの前提）
- 外気温予報（Open-Meteo、外部公開版と共通）との組み合わせ
- 部屋・エアコンのプロファイル設定（畳数、断熱性、エアコン性能等）
- 予冷シミュレーション：目標室温までの到達時間の計算
- 本日の効率窓（外気温が低く効率の良い連続時間帯）を検出し、「いつ強運転を開始すべきか」を提示
- 強運転→維持運転への切り替えタイミング提示
- kumaguma0918.com サブドメインでの内部限定公開（Cloudflare Access等で保護）

**やらないこと（初期スコープ外）**
- エアコンの自動制御（HA経由でのON/OFF・温度設定の自動操作）→ 将来拡張（3.3）
- 複数部屋・複数台エアコンの同時最適化
- 学習機能（過去の実績から自動補正するMLモデル）→ 将来拡張（3.4）
- AI（LLM API）連携 → 外部版と同じ方針で不採用。計算はすべて物理モデル・ルールベースで実施

### 1.3 利用者と利用シーン

| 項目 | 内容 |
|---|---|
| 利用者 | ショウタ本人のみ |
| 利用シーン | 外出先から帰宅前に、本日の効率窓（今が好機か／これから来るか／もう終わったか）を確認する場面。または在宅時に「あと何分で涼しくなるか」を確認する場面 |
| デバイス | スマートフォン（外出先からCloudflare Tunnel経由でアクセス） |

> 確定（2026-07-02改訂）: 到着予定時刻の入力（個別の帰宅時刻に合わせた運転開始逆算）は廃止したため、「外出先から帰宅前に確認」する際も、到着時刻に合わせた個別プランではなく、本日の効率窓の状態（今/今後/終了）のみを見る形になる。この範囲で要件を満たすと判断し、現状維持とする。
| アクセス制御 | Cloudflare Access（既存のEntra ID + FIDO2構成を流用） |

### 1.5 コスト方針

- Open-Meteo：無料
- Home Assistant：自宅サーバーで稼働中の既存資産を利用（追加コストなし）
- ホスティング：自宅home lab内（既存のCloudflare Tunnel経由で公開、Vercel等の外部ホスティングは使わない想定）
- LLM API等の従量課金サービスは外部版同様不採用

### 1.6 非機能要件

| 項目 | 要件 |
|---|---|
| 可用性 | 個人利用前提。home labのネットワーク状態に依存（既知の制約として許容） |
| パフォーマンス | シミュレーション計算は同期的に1秒以内で完了する想定（軽量な物理モデルのため） |
| セキュリティ | Cloudflare Access配下に配置し、Entra ID認証必須。HAのAPIトークンは環境変数で管理しコードに含めない |
| データ保存 | 部屋プロファイルはローカル（SQLite等）に保存。実測値の長期保存はHA側のHistory機能に委譲し本ツールでは持たない |
| 対応ブラウザ | モダンブラウザ（モバイル中心） |

### 1.7 制約・前提

- Home AssistantのAPIから取得できる室温センサーが既に存在していることを前提とする（確定: Nature Remoを室温・湿度センサーとして使用。HA上でNature Remo連携が設定済みであることを前提とする）
- 確定: Nature Remoはクラウド経由でのデータ更新のため、**取得値が数分〜十数分前の値になる可能性がある**。シミュレーションは「現在室温」として扱うが、UI上に実測値の取得時刻（タイムスタンプ）を併記し、利用者がズレを認識できるようにする
- 確認推奨: Nature Remo本体の設置位置（コンセント付近等）によっては、部屋の代表的な温度と実測値がズレる場合がある。設置位置が窓際・日射の影響を受けやすい場所でないか、運用開始前に一度確認する
- 予冷シミュレーションは簡易物理モデルであり、完全な熱力学計算ではない。実測値との比較（F-08）で継続的に精度を確認し、必要に応じてパラメータを調整する運用とする
- 確定（2026-07-02改訂）: 「到着予定時刻」の入力は廃止した。当初は帰宅時刻からの逆算モデルだったが、本サービスの根本コンセプト（外気温が低い効率窓を狙う予冷戦略）と乖離していたため、効率窓ベースのモデルに置き換えた（2.4参照）。これに伴い、旧3.2「帰宅時間の自動取得」は前提が消滅したため削除した
- 確定（2026-07-02改訂）: 湿度（F-02で取得）は、目標室温のおすすめ値算出（不快指数DIベース、F-11）に使用する。予冷シミュレーションの物理モデル自体（熱負荷計算）には引き続き使用しない
- 確定: 本サービスは**冷房（夏季）利用のみを対象**とする。暖房（冬季）への対応は初期スコープ外（暖房は熱負荷の方向が逆になり別モデルが必要なため）

## 2. 基本設計

### 2.1 システム構成図

```
┌──────────────┐
│ スマートフォン  │
│ (ブラウザ)      │
└──────┬───────┘
       │ ① HTTPS (Cloudflare Access経由、Entra ID認証)
       ▼
┌─────────────────────────┐
│ Cloudflare Tunnel          │  既存のkumaguma-tunnel基盤
└──────────┬──────────────┘
           │
           ▼
┌─────────────────────────────────┐
│ アプリ本体（home lab内, 例: Docker host） │
│  - フロントエンド (React)              │
│  - バックエンド (FastAPI等)            │
│      ├─ ②外気温取得 → Open-Meteo      │
│      ├─ ③室内実測値取得 → Home Assistant │
│      ├─ ④部屋プロファイルDB (SQLite)    │
│      └─ ⑤予冷シミュレーション計算ロジック │
└─────────────────────────────────┘
```

外部版と異なり、バックエンド（API集約・計算処理）を持つ構成とする。理由：
- Home AssistantのAPIトークンをフロントに露出させたくない
- 予冷シミュレーションの計算ロジックをサーバー側に集約し、将来の自動制御連携（3.3）に拡張しやすくする

### 2.2 ホスティング構成

| レイヤー | 技術 | 役割 |
|---|---|---|
| フロントエンド | React + Vite | UI表示 |
| バックエンド | FastAPI（Python） | API集約、シミュレーション計算 |
| 実行環境 | home lab内Dockerホスト（既存資産、192.168.100.30） | コンテナとして稼働。ESPRIMO Q556/Rは対象外（既存Dockerホストに確定） |
| 公開経路 | Cloudflare Tunnel + Access | 外部からの安全なアクセス |
| データ保存 | SQLite（部屋プロファイル） | 軽量・追加ミドルウェア不要 |
| 外部API | Open-Meteo、Home Assistant REST API | データ取得元 |

### 2.3 データフロー

1. ユーザーがブラウザでアクセス → Cloudflare AccessでEntra ID認証
2. フロントエンドがバックエンドAPIを呼び出し、以下を要求：
   - 当日の外気温予報（バックエンドがOpen-Meteoから取得）
   - 現在の室温・湿度（バックエンドがHome Assistant REST APIから取得）
   - 保存済みの部屋プロファイル（畳数、断熱性、エアコン性能）
3. ユーザーが目標室温を入力（未入力時は現在の室内湿度からのおすすめ値を使用、F-11）
4. バックエンドが当日予報から効率窓（最長の高効率連続時間帯）を検出し、予冷シミュレーションを計算して以下を返却：
   - 推奨運転開始時刻（効率窓の開始時刻、または既に窓の中であれば現在時刻）
   - 目標室温到達までの推定時間
   - 強運転→維持運転の切替推奨タイミング（効率窓の終了時刻、目標室温にそれより早く到達する場合はその時刻）
5. フロントエンドがグラフ・タイムラインで結果を表示
6. （F-08）実際の室温推移をHAから定期取得し、予測値と並べて比較表示

### 2.4 予冷シミュレーションの計算モデル

> **2026-07-02改訂**: 本節は「到着予定時刻からの逆算モデル」から「効率窓ベースのモデル」に全面的に置き換えた。根本コンセプト（外部版1.1、本書1.1参照）に立ち返り、外気温が低く効率の良い時間帯を狙って強運転を行い、効率が悪化するタイミングで維持運転に切り替える設計とする。

#### 2.4.1 入力パラメータ

| パラメータ | 取得元 | 例 |
|---|---|---|
| 現在室温 | Home Assistant（実測） | 29.5℃ |
| 目標室温 | ユーザー入力、または2.4.1aのおすすめ値 | 26.0℃ |
| 外気温・効率（時間別） | Open-Meteo（外部版と同じ効率区分: excellent/good/fair/poor） | 各時間の予報値 |
| 部屋の畳数 | プロファイル設定 | 14畳 |
| 断熱性レベル | プロファイル設定（簡易区分） | 木造/RC造などの区分で係数を補正 |
| エアコン冷房能力 | プロファイル設定 | 4.0kW等、機種スペックから入力 |
| 室内発熱（人数・PC等） | プロファイル設定（`occupant_load`、簡易固定値） | 軽い補正項として扱う |

#### 2.4.1a 目標室温おすすめ値（F-11）

現在の室内湿度から、不快指数(DI)を用いて目標室温のおすすめ値を逆算する。

```
DI = 0.81×T + 0.01×RH×(0.99×T - 14.3) + 46.3   （T: 室温, RH: 相対湿度%）

DI_TARGET = 74（「快い」〜「やや暑い」境界付近を目安値とする）

T_recommend = (DI_TARGET - 46.3 + 0.143×RH) / (0.81 + 0.0099×RH)
```

算出値は24.0〜29.0℃の範囲にクランプし、0.5℃刻みに丸める。室内湿度が取得できない場合はおすすめ値を算出せず、ユーザーの手動入力を必須とする。ユーザーはいつでも手動で上書きできる（自動提案であり強制ではない）。

#### 2.4.2 モデルの考え方

簡易熱負荷モデルを採用する（厳密な熱力学シミュレーションは行わない）。単位はSI単位（kW・kJ・℃・秒）で明示的に統一し、畳数の重複カウントを避ける。

**Step A: 本日の効率窓を検出する**

当日の外気温予報のうち、効率が excellent または good な時間帯を連続区間としてグルーピングし、最も長い区間を「効率窓」とする（外部版のAutoCommentロジックと同じ手法をバックエンドに実装）。

**Step B: 運転開始時刻を決定する**

| 現在時刻の状態 | 運転開始時刻 |
|---|---|
| 効率窓の中（今が好機） | 現在時刻（今すぐ開始） |
| 効率窓がこれから来る | 効率窓の開始時刻 |
| 本日の効率窓は既に終了 | シミュレーション不可。「本日の効率的な時間帯は終了しました。次の好機は明日以降です」と表示 |
| 本日は効率窓が存在しない（一日中暑い等） | 参考値として、今から開始した場合の計算結果を注記付きで表示 |

**Step C: 物理モデルで目標室温までの到達時間を計算する**

```
① 熱侵入(kW) = 断熱性係数(kW/畳/℃) × 断熱性レベル係数 × 畳数 × (外気温 - 目標室温)

② 実効冷房能力(kW) = エアコン冷房能力 - 熱侵入 - 室内発熱(kW、プロファイルのoccupant_load)

③ 室内の熱容量(kJ/℃) = 熱容量係数(kJ/℃/畳) × 畳数

④ 除去すべき熱量(kJ) = 熱容量 × (現在室温 - 目標室温)

⑤ 到達時間(分) = 除去すべき熱量(kJ) ÷ 実効冷房能力(kW) ÷ 60
   ※ kW = kJ/秒 のため、kJ ÷ kW = 秒
   ※ 外気温には運転開始時刻の時間帯の予報値を用いる（静的近似モデル、下記参照）
```

**初期係数（仮値、運用しながら補正）：**

| 係数 | 値（仮） | 単位 |
|---|---|---|
| 断熱性係数 | 0.012 | kW/畳/℃ |
| 断熱性レベル係数 | 木造1.0 / RC造0.7 / その他0.9 | 無次元 |
| 室内発熱（occupant_load初期値） | 0.3 | kW（プロファイルで保持、固定値運用） |
| 熱容量係数 | 60 | kJ/℃/畳 |

**検証例（14畳・木造・外気温33℃・目標26℃・現在29.5℃・エアコン4.0kW）：**

```
熱侵入 = 0.012 × 1.0 × 14 × (33-26) = 1.18 kW
実効冷房能力 = 4.0 - 1.18 - 0.3 = 2.52 kW
熱容量 = 60 × 14 = 840 kJ/℃
除去すべき熱量 = 840 × (29.5-26) = 2,940 kJ
到達時間 = 2,940 ÷ 2.52 ÷ 60 ≈ 19.4分
```

実効冷房能力が0以下になる場合（外気温が高すぎる・エアコン能力不足等）は「目標室温への到達は困難」として警告表示する（2.8参照）。

**Step D: 維持運転への切替時刻を決定する**

```
切替時刻 = min(効率窓の終了時刻, 運転開始時刻 + 到達時間)
```

すなわち、目標室温に効率窓終了より早く到達すればその時点で維持運転に切り替え、到達が間に合わなければ効率窓終了時点で切り替える（それ以上は外気温効率が悪化しており強運転を続ける効率的メリットが薄いため）。後者の場合は「効率的な時間帯内には目標室温へ到達できません」と警告表示する（2.8参照）。

> 確定: このモデルは「外気温・冷房能力が運転開始時刻の予報値から一定」という前提の静的近似モデルである。実際は強運転中も外気温が変動するため、到達時間はあくまで目安。UI上に「簡易計算のため目安です」等のツールチップ・注記を表示する（F-04の表示要件として追加）。

> 確定: 室内発熱の初期値0.3kWは「居住者1名＋PC等の電子機器」を想定した仮の固定値。`occupant_load`としてプロファイルに保持し、計算にもプロファイルの保存値をそのまま使用する（初期実装ではユーザーが人数や機器構成から動的に按分計算する機能はなく、固定値運用とする。動的な按分計算は将来拡張3.4以降で検討）。

#### 2.4.3 出力

- 推奨運転開始時刻（効率窓ベース）
- 強運転継続時間（分）
- 維持運転への切替推奨時刻（効率窓終了、または目標到達のどちらか早い方）
- 目標室温に到達できたか（`target_reached`）

### 2.7 外部・内部API仕様

**Open-Meteo（外部版と共通）**
```
GET https://api.open-meteo.com/v1/forecast?...
```

**Home Assistant REST API（想定）**
```
GET {HA_BASE_URL}/api/states/{entity_id}
Header: Authorization: Bearer {HA_LONG_LIVED_TOKEN}
```
- `entity_id`はプロファイルごとに室温・湿度センサーを紐付け設定
- `HA_LONG_LIVED_TOKEN`はバックエンドの環境変数として保持（フロントに露出させない）

**バックエンド内部API（フロントエンド向け）**
```
GET  /api/status          → 現在の室温・外気温まとめ取得
  Response: { outside_temp_forecast[], current_room_temp, current_humidity, observed_at, is_stale, ha_error, recommended_target_temp }
GET  /api/profile          → プロファイル取得（単一固定）
POST /api/profile          → プロファイル更新
POST /api/simulate          → シミュレーション実行
  Body: { target_temp }  ※ target_tempを省略した場合、現在の室内湿度からのおすすめ値を使用する
  Response: { start_time, strong_duration_min, switch_time, used_target_temp, target_reached, predicted_curve[], warning }
```

### 2.8 エラーハンドリング方針

| 状況 | 挙動 |
|---|---|
| Home Assistant接続失敗 | 室温は「取得不可」と表示し、外気温のみのシンプル表示にフォールバック |
| Open-Meteo通信失敗 | 外部版と同様、エラー表示 |
| プロファイル未登録 | シミュレーション実行不可。先にプロファイル登録を促す |
| シミュレーション計算異常値（負の時間、実効冷房能力0以下、極端な長時間等） | 「計算できませんでした」または「目標室温への到達は困難です」と表示。**確定: 到達時間が480分（8時間）を超える場合も異常値として警告表示し、目標室温の見直しを促す** |
| Home Assistant応答が極端に古い | **確定: 取得値のタイムスタンプが30分以上前の場合「データが古い」旨をUIに表示する**（Nature Remoの通常更新間隔15〜20分に対し、誤検知と検知漏れのバランスを取った値） |
| 本日の効率窓が既に終了 | シミュレーション不可。「本日の効率的な時間帯はすでに終了しました。次の好機は明日以降です」と表示 |
| 本日は効率窓が存在しない | 参考値として今から開始した場合の計算結果を、注記付きで表示 |
| 効率窓終了までに目標室温へ到達できない | 「効率的な時間帯内には目標室温へ到達できません。目標室温を上げるか、日を改めての検討を推奨します」と警告表示（`target_reached: false`） |
| 目標室温が未指定かつ室内湿度も取得不可 | おすすめ値を算出できないため、目標室温の手動入力を促す |

> タイムゾーンはOpen-Meteo・Home Assistant双方とも`Asia/Tokyo`固定で運用し、ズレが生じないようにする。

### 2.9 セキュリティ設計
